## Checkpoint 01 — Nabu dual-bank metadata + sparse alignment

The image begins with two 256-byte header banks (`0x000–0x0ff` and `0x100–0x1ff`); the second repeats core ILM/DLM metadata but has different mode/auxiliary descriptors. The public Linux NT36xxx update driver documents core ILM/DLM `file:sram:size_minus_one`, info-entry `sram:size_minus_one:file:crc`, and CRC register writes. This exact dual-bank arrangement is specific to this Nabu image, so the generic driver parser cannot blindly treat all entries through `0x200` as one flat list.

Typed Rust representation in `novatek_layout.rs` rebuilds the entire **512-byte header** by serializing named scalar fields. It explicitly carries **opaque controller CRC words supplied by the metadata**; these are not independently recomputed. It does not copy executable/vendor payload bytes.

| Region | File range | Size | Independent source coverage |
| --- | --- | ---: | --- |
| Nabu metadata banks | `[0x00000, 0x00200)` | 512 | Deterministic structural serializer; **stored vendor CRC scalars required** |
| ILM firmware payload | `[0x00200, 0x1ac80)` | 109,184 | **Unimplemented executable/data; not copied** |
| Padding ILM–DLM | `[0x1ac80, 0x22000)` | 29,568 | Independently zero-generated, strict all-zero precondition |
| DLM firmware payload | `[0x22000, 0x2e190)` | 49,552 | **Unimplemented payload; not copied** |
| Tail/trailer and other data | `[0x2e190, 0x30000)` | 7,792 | Unimplemented except verified final `NVT` marker |

Thus the **only verified independently generated bytes from a pure layout rule are 29,568 bytes of zero padding**. The 512-byte header additionally requires original per-image metadata scalars (especially 10 controller CRC fields). No independently decompiled instruction count can yet be claimed.

## Processor/ISA evidence and open work

The image has a standard Novatek NT36xxx-family ILM/DLM transport structure, but this does **not** determine its internal microcontroller ISA. The ILM payload starts with a dense 32-bit pointer/handler vector table; execution begins elsewhere. No authoritative identification of the NT36523 firmware's CPU model/ISA or independently decoded instruction traces is yet available; do **not** assume ARM, Thumb, MIPS, 8051, RISC-V or Andes NDS32 solely from byte resemblance. The next tasks are: establish ISA through hardware/vendor/toolchain documentation plus independent decoder validation; identify real code/data boundaries; derive and test the controller CRC algorithm; implement original executable code from typed instructions and validate reference bytes. No flashable image can be generated from this source yet.

Public protocol references (not firmware content):

- Linux NT36xxx driver parser: https://patchew.org/linux/20241015-nt36xxx-v1-0-3919d0bffee6%40gmail.com/20241015-nt36xxx-v1-2-3919d0bffee6%40gmail.com/
- NT36523 chip mapping in touchscreen driver: https://android.googlesource.com/kernel/google-modules/touch/novatek_touch/

## Checkpoint 02 — Strict full-image provenance and end padding

The correct 196,608-byte postmarketOS image has another reserved area
`[0x2f900, 0x2fffd)`, all **1,789 zero bytes**, followed by the constant
three-byte `NVT` terminator `[0x2fffd, 0x30000)`. A typed writer emits
these bytes without reading the vendor payload; any nonzero reference in
the reserved range is **rejected**, not silently overwritten.

`novatek_layout::coverage()` describes **every byte** using seven mutually
exclusive, gapless regions and refuses overlaps, negative or missing ranges.
Only independently provable regions count as source-derived data.

| File region | Bytes | Status |
| --- | ---: | --- |
| `[0x00000,0x00200)` | 512 | Structured header; vendor CRC scalar inputs remain opaque |
| `[0x00200,0x1ac80)` | 109,184 | ILM executable/data unknown |
| `[0x1ac80,0x22000)` | 29,568 | Verified independently emitted zeros |
| `[0x22000,0x2e190)` | 49,552 | DLM executable/data unknown |
| `[0x2e190,0x2f900)` | 6,000 | Controller calibration/trailer unknown |
| `[0x2f900,0x2fffd)` | 1,789 | Verified independently emitted zeros |
| `[0x2fffd,0x30000)` | 3 | Independently emitted fixed `NVT` marker |

Totals: **31,360 bytes** of fully source-independent layout constants
(`29,568 + 1,789 + 3`), plus **512 bytes** of metadata serializable from
external supplied scalar fields, and **164,736 unimplemented payload bytes**
(`109,184 + 49,552 + 6,000`). These totals sum to **196,608**.
No part of the unknown executable/data regions is counted as reconstructed,
even when it happens to contain zeros. Do not call this a complete firmware.

Validate and emit using the *correct* private reference:

```sh

cargo run --offline --locked -p firmware-tools --bin novatek-nabu -- emit-tail-padding /private/novatek_nt36523_fw.bin /tmp/novatek-endpad.bin
cargo run --offline --locked -p firmware-tools --bin novatek-nabu -- emit-marker /private/novatek_nt36523_fw.bin /tmp/novatek-end-marker.bin
```

## Checkpoint 03 — Hole-rejecting structural image builder

Added `novatek_reassemble.rs`, a **Novatek-only** assembler that operates
from the typed layout and optional *independently authored* payload inputs.
It makes a full, sparse projection of the seven classified ranges without
materializing unknown bytes. Three explicit holes are reported in order:

1. ILM `[0x200,0x1ac80)` — 109,184 bytes.
2. DLM `[0x22000,0x2e190)` — 49,552 bytes.
3. Auxiliary/calibration `[0x2e190,0x2f900)` — 6,000 bytes.

`assemble_structural_unverified()` **fails on the first missing or wrongly
sized authored payload**, rejecting any implicit OEM byte copy or zero fill.
Once all three external source payloads are supplied, it serializes a complete
image using only the authored buffers, typed metadata fields, independently
generated padding, and `NVT` suffix. Synthetic tests cover missing ILM/DLM/
auxiliary, wrong lengths, gapless byte-for-byte assembly, and a permanent
`is_hardware_crc_verified()==false` status.

The explicit optional CLI `assemble-structural-unverified` requires a metadata
reference *and three distinct authored payload files*. It is intentionally
labelled **UNVERIFIED**: no checksum algorithm was independently established,
and supplying proprietary reference slices would not count as firmware
decompilation. We have **not** used the original ILM/DLM/auxiliary bytes as
input to claim a full byte-identical reconstruction. Therefore **independent
executable coverage remains zero bytes**.

Command syntax:

```sh
cargo run --offline --locked -p firmware-tools --bin novatek-nabu -- \
  assemble-structural-unverified /private/novatek_nt36523_fw.bin \
  /authored/ilm.bin /authored/dlm.bin /authored/auxiliary.bin \
  /tmp/novatek-structural-unverified.bin
```

Although test data can pass this structural assembly, **no generated full
reference firmware is present**: the remaining 164,736 bytes still require
source implementation and checksum verification.

### ISA investigation

The Nabu touchscreen compatible is `novatek,NVT-ts-spi`, not the separate
similarly named NT36523 DSI *display panel* driver. The public DTS names
`novatek,swrst-n8-addr` and the firmware starts with a mixed, primarily
16-bit-aligned interrupt/vector-pointer array after file offset `0x200`.
These observations alone do not identify the MCU ISA. Recent Ghidra supports
NDS32 and an independent NDS32 decode comparison is worth testing, but **the
firmware's CPU architecture remains unproven** without well-formed code flow
and vendor corroboration. Do not assert that `N8` implies Andes N8.

Candidate CRC-32 ISO-HDLC, no-XOR, init-0, reversed input, and Adler32
values do not match both independently stored core CRC fields. The values
must remain opaque until the exact controller hardware CRC algorithm is known.

## Checkpoint 04 — Candidate interrupt/handler vectors and ILM start

Compared the correct postmarketOS image and the incorrect upstream revision:
**both** contain a 128-word, little-endian array at file `[0x200,0x400)`
followed by **80 independently reconstructible zero bytes** at
`[0x400,0x450)`. Nonzero instruction-like words start at `0x450`.
The first table word is a controller-specific value (`0xa2010048` in the
reference); the remaining 127 words are opaque candidate vector/descriptors.
Some are *odd* (`0x4ddd`) while others are even (`0xc5ea`). They must
**not** be interpreted blindly as executable branch destinations or proof
of Thumb/NDS32/RISC-V. Each candidate address is bounded by ILM SRAM; the
first control word is explicitly excluded from that check.

`novatek_vector.rs` creates a **typed 512-byte candidate-vector table** from
externally supplied address scalars, validates bounds, and reserializes it;
the resulting output matches the correct reference byte-for-byte. It remains
**opaque vendor address data**, not independently authored executable code.
The `novatek-nabu` utility adds `emit-vector`, `verify-vectors`, and
`emit-vector-padding` to independently emit/verify the 80 zero bytes.
The strict image-builder source plan now additionally requires an external
vector table and separately authored ILM code/data beginning at `0x450`.
