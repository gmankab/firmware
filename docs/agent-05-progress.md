## CDSP reference and layout

CDSP reference filename: `cdsp.mbn`, SHA-256 `febeae7b8e47bad4eeabc159a3c24b74cda26dfa12b384c31de5de30817e06ea`. The file is private and is **not committed**. This is an ELF32 little-endian Qualcomm DSP6 image with 12 ELF program headers, `e_machine=164`, `e_flags=0x66` (Hexagon V66), and entry **physical** address `0x96c00000`.

The first executable `PT_LOAD` has `p_offset=0x3000`, `p_vaddr=0xfe000000`, `p_paddr=0x96c00000`, `p_filesz=0x37b34` and `p_memsz=0xad000`. These three address spaces are **not interchangeable**. MBN hashes, data/BSS, authentication and all remaining executable segments are separate from the reconstructed instruction bytes.

## Checkpoint 01 — nine Hexagon scalar packets

**Independent source-derived output:** file offsets **`0x3000–0x3024`**, 36 bytes. The first eight packets are a direct jump to the last vector slot, six self-branch vectors and a dispatch jump into the first executable segment; packet nine sets the `r0` argument register to zero. The last dispatch target is the physical address `0x96c00cac`. Hexagon assembler-backed constructors and Rust encoder are independent, both refusing unsupported displacement/operand forms. The emitter is `cdsp_boot::build_entry`; all 36 bytes compare exactly with the private reference. Generated byte-range SHA-256: `b07fd5fc8ef3f923183158ce35e91f6210b0f4e8091ddbf4304bccde5d910f7c`.

This is **36 executable instruction bytes, not 36 bytes of the full firmware**. The rest of the first executable segment (`0x3024–0x3ab34`) and all other segments are unimplemented. The first two words at file `0x3024` and `0x3028` use encodings not recognized by the available LLVM 6 Hexagon v60/v65 decoder; do **not** replace those bytes with a different canonical encoding that merely decompiles to similar semantics. Later instruction packets may have V66 features. The V66 code's runtime correctness and authentication remain unverified.

### Reproduction

```sh
# Build a 36-byte fragment from Rust, never from the OEM firmware file:
cargo run --offline --locked -p firmware-tools --bin cdsp-rebuild -- \
  emit-entry /tmp/cdsp-entry.bin

# Validate the exact reference image and compare just the 36 reconstructed bytes:
cargo run --offline --locked -p firmware-tools --bin cdsp-rebuild -- \
  verify-entry /private/qcom/sm8150/Xiaomi/nabu/cdsp.mbn

# Independent Hexagon assembler round-trip of the same nine named operations:
python3 tools/verify-cdsp-hexagon-entry.py \
  --llvm-mc /path/to/llvm6/bin/llvm-mc \
  --rust-output /tmp/cdsp-entry.bin \
  --reference /private/qcom/sm8150/Xiaomi/nabu/cdsp.mbn

cargo test --workspace --offline --locked
cargo build --workspace --release --offline --locked
python3 -m unittest discover -s tests -p 'test_*.py'
```

The LLVM 6 Hexagon `llvm-mc -mcpu=hexagonv60` provides independent encoding verification of these simple packets, but **does not identify all V66 instructions**. The supplied LLVM 22 cross-toolchain binaries are present, but its host `libc++.so.1`, `libc++abi.so.1` and `libunwind.so.1` dependencies are unavailable here. The included `.so` variants in `target/hexagon-unknown-linux-musl/usr/lib` are 32-bit Hexagon DSP binaries and cannot satisfy x86-64 host dependencies. Network DNS is disabled; apt-based installation was unavailable. This blocks higher-coverage Hexagon V66 disassembly, not the checked 36-byte entry emitter.
