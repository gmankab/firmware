## CDSP reference and layout

CDSP reference filename: `cdsp.mbn`, SHA-256 `febeae7b8e47bad4eeabc159a3c24b74cda26dfa12b384c31de5de30817e06ea`. The file is private and is **not committed**. This is an ELF32 little-endian Qualcomm DSP6 image with 12 ELF program headers, `e_machine=164`, `e_flags=0x66` (Hexagon V66), and entry **physical** address `0x96c00000`.

The first executable `PT_LOAD` has `p_offset=0x3000`, `p_vaddr=0xfe000000`, `p_paddr=0x96c00000`, `p_filesz=0x37b34` and `p_memsz=0xad000`. These three address spaces are **not interchangeable**. MBN hashes, data/BSS, authentication and all remaining executable segments are separate from the reconstructed instruction bytes.

## Checkpoint 01 — nine Hexagon scalar packets

**Independent source-derived output:** file offsets **`0x3000–0x3024`**, 36 bytes. The first eight packets are a direct jump to the last vector slot, six self-branch vectors and a dispatch jump into the first executable segment; packet nine sets the `r0` argument register to zero. The last dispatch target is the physical address `0x96c00cac`. Hexagon assembler-backed constructors and Rust encoder are independent, both refusing unsupported displacement/operand forms. The emitter is `cdsp_boot::build_entry`; all 36 bytes compare exactly with the private reference. Generated byte-range SHA-256: `b07fd5fc8ef3f923183158ce35e91f6210b0f4e8091ddbf4304bccde5d910f7c`.

This is **36 executable instruction bytes, not 36 bytes of the full firmware**. The rest of the first executable segment (`0x3024–0x3ab34`) and all other segments are unimplemented. The first two words at file `0x3024` and `0x3028` use encodings not recognized by the available LLVM 6 Hexagon v60/v65 decoder; do **not** replace those bytes with a different canonical encoding that merely decompiles to similar semantics. Later instruction packets may have V66 features. The V66 code's runtime correctness and authentication remain unverified.

### Reproduction

```sh
# Build a 36-byte fragment from Rust, never from the OEM firmware file:
cargo run --offline --locked -p firmware-tools --bin cdsp-rebuild -- \
  emit-entry /tmp/cdsp-entry.bin

# Validate the exact reference image and compare just the 36 reconstructed bytes:
cargo run --offline --locked -p firmware-tools --bin cdsp-rebuild -- \
  verify-entry /private/qcom/sm8150/Xiaomi/nabu/cdsp.mbn

# Independent Hexagon assembler round-trip of the same nine named operations:
python3 tools/verify-cdsp-hexagon-entry.py \
  --llvm-mc /path/to/llvm6/bin/llvm-mc \
  --rust-output /tmp/cdsp-entry.bin \
  --reference /private/qcom/sm8150/Xiaomi/nabu/cdsp.mbn

cargo test --workspace --offline --locked
cargo build --workspace --release --offline --locked
python3 -m unittest discover -s tests -p 'test_*.py'
```

The LLVM 6 Hexagon `llvm-mc -mcpu=hexagonv60` provides independent encoding verification of these simple packets, but **does not identify all V66 instructions**. The supplied LLVM 22 cross-toolchain binaries are present, but its host `libc++.so.1`, `libc++abi.so.1` and `libunwind.so.1` dependencies are unavailable here. The included `.so` variants in `target/hexagon-unknown-linux-musl/usr/lib` are 32-bit Hexagon DSP binaries and cannot satisfy x86-64 host dependencies. Network DNS is disabled; apt-based installation was unavailable. This blocks higher-coverage Hexagon V66 disassembly, not the checked 36-byte entry emitter.

## Checkpoint 02 — privileged Hexagon V66 initialization

An additional eight **typed** four-byte packets reconstruct file offsets `0x3024–0x3044`, extending the independently generated CDSP prefix to **68 consecutive bytes** (`0x3000–0x3044`). The instructions are `SSR=R0`, `R0=SYSCFG`, two `setbit` operations, `SYSCFG=R0`, `dckill`, `ickill`, and a direct branch to runtime physical address `0x96c00144`. The prefix SHA-256 is `860bcbbac78fe0282fe36b704c621acddd2bdeb66623b3720c2c5a784cd15715`.

The two V66 special-register forms are reconstructed from checked system-register selector and general-register fields. LLVM 6 assembles the first nine packets and the two `setbit` instructions but **cannot assemble/decode all special-register or cache-operation forms**. The separately supplied Rizin Hexagon V6 decoder identifies **all seventeen packets**, their privilege/cache semantics, packet flags and exact branch targets; see `tools/verify-cdsp-v66-init.py`. This is decoder corroboration, **not an independent second-assembler round-trip for all 68 bytes**. Comparing the typed Rust output directly to the private original verifies all 68 bytes without copying reference instructions into the emitter.

Reproduction:

```sh
cargo run --offline --locked -p firmware-tools --bin cdsp-rebuild -- \
  emit-init-prefix /tmp/cdsp-init-prefix.bin
cargo run --offline --locked -p firmware-tools --bin cdsp-rebuild -- \
  verify-init-prefix /private/qcom/sm8150/Xiaomi/nabu/cdsp.mbn

# Set LD_LIBRARY_PATH if using the staged Ubuntu 24 Rizin runtime:
# export LD_LIBRARY_PATH=/path/to/ubuntu-runtime/usr/lib/x86_64-linux-gnu

  --rz-asm /path/to/rizin-staged/opt/nabu-rizin/bin/rz-asm \
  --rust-output /tmp/cdsp-init-prefix.bin \
  --reference /private/qcom/sm8150/Xiaomi/nabu/cdsp.mbn
```

The **first uncovered word remains at `0x3044`**. The reference contains `0x00000000` there and the independent decoder treats it as invalid code, while decoded instructions resume at `0x3048`. Whether it is padding, deliberate invalid opcode, or a special-use word must be established before counting or generating it. The branch at `0x3040` points into later code that is not reconstructed, so this prefix cannot execute in isolation.

## Checkpoint 03 — separate CDSP supervisor-state reset function

An **independent, disconnected 44-byte function** has been implemented at file offsets **`0x3d40–0x3d6c`**, mapped physical addresses **`0x96c00d40–0x96c00d6c`**. It is **not contiguous** with the 68-byte entry prefix; the interval `0x3044–0x3d40` is not reconstructed and must remain a hole in any CDSP layout plan. The function reads SYSCFG into `r15`, clears a bit, writes it back, performs `isync/ickill`, restores SYSCFG flags, subtracts a relocation base from LR, and branches through LR. The 44 generated bytes have SHA-256 `124ccf1d0f6f60daf2b0ea53a34eff16dc45383cabc44515d04d9c14e0e949fc` and exactly match the private CDSP reference.

The typed `ScalarPacket` encoder now covers `clrbit`, OR-immediate, register subtraction, register jump, `isync` and the previously verified V66 privileged instructions. Register field positions are independently checked with LLVM 6 assembly using multiple nontrivial operand combinations. LLVM 6 independently assembles the ordinary bit/arithmetic/return instructions; Rizin separately decodes **all eleven** instructions (including V66 privileged forms) via `--profile syscfg-reset`, checking byte width, packet markers, register operands and instruction order. As before, Rizin decoding is corroboration **not** independent LLVM reconstruction of unsupported V66 opcodes.

## Checkpoint 05 — complete supervisor cluster and relocation trampoline

The previously missing 20 bytes at file `[0x3d6c,0x3d80)` are a
**Hexagon relocation trampoline**. A named `FP=##-0x1fff280` extended
assignment occupies two words (continuation marker on the second), followed
by `LR=add(LR,R25)` in the same packet; singleton `FP=add(FP,R25)` and
`jumpr FP` finish the trampoline. The typed Rust constructor
`encode_extended_assignment` models split immediate bitfields and packet
parse markers; `AddRegisters` has independent register-field tests.

LLVM6 independently assembles this five-word trampoline from:

```asm
{
 r30 = ##-0x1fff280
 r31 = add(r31,r25)
}
{ r30 = add(r30,r25) }
{ jumpr r30 }
```

Thus the three functions are **84 contiguous independently generated
executable bytes** at `[0x3d40,0x3d94)` (physical
`[0x96c00d40,0x96c00d94)`). The separate entry prefix is still 68
bytes. Total verified executable content is **152 bytes across two disjoint
regions** (68 + 84), not a contiguous 152-byte boot image. This accurately
accounts for all supervisor bytes without placeholder instructions or
reference copying. The base checkpoint-50 bundle remains unavailable;
branch ancestry remains `69ebf0d`.


## Checkpoint 06 — two adjacent TLB maintenance functions

At file `[0x3dfc,0x3e38)` (physical `[0x96c00dfc,0x96c00e38)`), two
standalone functions total **60 contiguous reconstructed bytes**. The first
builds 16-bit TLB attributes from logical shifts, bit-field insertion and a
register mask, then executes `tlbw(R3:2,R0)`, `isync` and returns. The second
sets `R3:2 = combine(#0,#0)`, executes `tlbw`, synchronizes and returns.
Hexagon packet markers are preserved explicitly, using typed register fields
and checked immediate/range constraints; **no private opcode arrays are copied**.

`tools/verify-cdsp-tlb.py` independently assembles the 13 non-TLB instructions
(52 bytes) with LLVM6 and uses Rizin V66 to decode **all 15 instructions**.
Rizin corroborates the two V66 `tlbw` encodings, but does not independently
*assemble* them; this distinction matters. The 60 emitted bytes match the
private CDSP reference with zero differences. New typed constructs include
logical right shift, register bit-field insert, unsigned 12-bit immediate,
zeroed register pair, TLB write indexed by R0, and checked Hexagon packet
parse markers.

The independent rebuild now covers **212 unique CDSP executable bytes**
in three disjoint spans: entry `[0x3000,0x3044)` (68), supervisor
`[0x3d40,0x3d94)` (84), and TLB `[0x3dfc,0x3e38)` (60). The total is not one
contiguous run. There is still a 104-byte gap `[0x3d94,0x3dfc)` between
supervisor and TLB, and a large unreconstructed interval after 0x3044.
No full/signable CDSP firmware has been produced. The base checkpoint-50

Combined with checkpoint 06, this forms **112 contiguous exact bytes** at
`[0x3dc8,0x3e38)` (physical `[0x96c00dc8,0x96c00e38)`).

## Checkpoint 08 — contiguous CDSP supervisor and TLB initialization

The missing 13-instruction, 52-byte TLB table walker at file `[0x3d94,0x3dc8)`
(physical `[0x96c00d94,0x96c00dc8)`) is reconstructed in typed source. It
initializes a base address using a Hexagon `immext`/extended-ADD packet,
loads paired TLB words with post-increment, checks a 7-bit field, conditionally
rewrites it, programs the privileged `tlbw`, loops while entries are present,
then synchronizes and returns. New checked encodings cover postincrementing
64-bit loads, extractu, reversed unsigned subtraction, new-value branches,
compound P0 compare/backbranch, small add immediates, and extended ADD.

This joins **every byte of the independently authored supervisor/TLB region**:
`[0x3d40,0x3e38)` = **248 contiguous verified executable bytes**. The main
entry prefix `[0x3000,0x3044)` is separate and remains only 68 bytes.
**Cumulative independently generated executable coverage is 316 bytes in
TWO DISJOINT intervals**; the gap `[0x3044,0x3d40)` is still unimplemented.

LLVM6 independently reproduces 48 ordinary instruction bytes in the new
walker; it cannot assemble privileged `tlbw`. The independent Rizin Hexagon
V6 decoder confirms the full 13-operation sequence, including the V66 TLB
write, while Rust output matches the private reference byte-for-byte.
An assembler-only temporary NOP is used solely to maintain layout for the
LLVM comparison; the real Rust implementation contains the typed TLB write,

## Checkpoint 09 — TLB register clear and indexed single-entry invalidation

At private CDSP file `[0x3e38,0x3e78)` (physical addresses
`[0x96c00e38,0x96c00e78)`), 64 more bytes are reconstructed from typed Hexagon
operations, contiguous with the pre-existing supervisor/TLB span. The first
28-byte loop clears all 127 numbered TLB entries using a register-compare,
a packet-local `P0.new` early return and a negative backedge. The second
36-byte function constructs a single entry's address using an independently
assembled 32-bit immediate extension, shift and add, then writes the TLB.

The special 32-bit `R0=#0; R3:2=combine(#0,#0)` duplex was independently
assembled by LLVM Hexagon. Its parse bits are **duplex-specific** and must not
be overwritten using the ordinary Hexagon continuation/final marker helper.
`JumpBackward` accepts only aligned short *negative* offsets; arithmetic shift
and `P0=cmp.eq(Rx,Ry)` constructors use checked register fields. The combined
supervisor/TLB cluster is **312 contiguous generated bytes** at file
`[0x3d40,0x3e78)`; the disjoint entry prefix remains 68 bytes. Thus 380 total
independently generated executable bytes are known, over two disjoint spans.

Independent LLVM6 output exactly matches **48 bytes** of the 64-byte extension.
Its scheduler swaps the trailing add/branch packet; both operations' operand
bitfields match independently after discarding their packet-marker bits
(8 additional bytes). LLVM6 cannot assemble the two Hexagon V66 `tlbw`
instructions (8 bytes); Rizin's V66 Hexagon decoder independently confirms
all 16 original instruction words and both TLB writes, but this is **decode
corroboration, not independent assembly**. Byte comparison against the private
reference yields 64/64 exact new bytes and 312/312 exact combined bytes, with
no original OEM code copied into Git. These routines are not a complete or
flashable CDSP image.
