# Agent 20-17: inherited NDS32 encoder audit

This audit applies to the inherited Agent 09 source at commit
`51b1f91f32d32542aa03e114f5a2f4d94b559e2a`. It records corrections for the
integration owner. Agent 17 has not changed the inherited implementation or
claimed additional executable coverage from this audit.

## Confirmed incorrect instruction descriptions

The inherited `branch_not_equal_to_a5()` allows comparison register `r5`.
That value selects a reserved subspace of the 16-bit BNES38 encoding rather
than an ordinary conditional comparison. GNU's Andes-contributed decoder
recognizes JR5, JRAL5, RET5 and the small EX9.IT form in this subspace.

| File offset | Runtime address | Encoded instruction | Actual operation | Incorrect claimed direct target |
| ---: | ---: | --- | --- | ---: |
| `0x484` | `0x284` | `0xdd22` | `jral5 r2` | `0x4c8` |
| `0x4cc` | `0x2cc` | `0xdd22` | `jral5 r2` | `0x510` |
| `0x51a` | `0x31a` | `0xdd22` | `jral5 r2` | `0x55e` |
| `0x572` | `0x372` | `0xdd2f` | `jral5 r15` | `0x5d0` |
| `0x5bc` | `0x3bc` | `0xdd2f` | `jral5 r15` | `0x61a` |
| `0x5c2` | `0x3c2` | `0xdd2f` | `jral5 r15` | `0x620` |

These are indirect calls, so their real destinations depend on register
values. The generated bytes may still compare exactly with the reference;
that comparison does not validate the stated control-flow semantics.

The integration owner should add a typed JRAL5 encoder, reject `r5` in
BNES38, replace these six uses, and correct the inherited direct-target
comments and progress descriptions. This correction should preserve the
emitted instruction bytes. A regression must distinguish JRAL5 from an
invalid BNES38 request; the inherited test currently asserts the misleading
BNES38 interpretation of `0xdd22`.

Primary references:

- GNU binutils `opcodes/nds32-dis.c`, special handling of `rt38 == 5`:
  https://gnu.googlesource.com/binutils-gdb/+/refs/tags/gdb-7.8-branchpoint/opcodes/nds32-dis.c
- GNU binutils opcode definitions, `INSN_JRAL5` and `N16_T5_JRAL5`:
  https://gnu.googlesource.com/binutils-gdb/+/3cb5e955a372f0303992340a164a21ca5cf6d006/include/opcode/nds32.h

## Compact register field mapping

NDS32 T45 instructions map their four-bit register field to
`r0..r11,r16..r19`, not `r0..r15`. The inherited
`shift_right_immediate()` and `subtract_reg_small()` incorrectly accept
`r12..r15` and reject the legal `r16..r19`. Their existing boot call sites
use `r0`, so this defect does not alter the currently generated prefix.

New encoders must use a checked mapping: registers 0 through 11 retain
their number, registers 16 through 19 encode as 12 through 15, and all
other registers are rejected. Test both ends of each valid range and the
invalid middle range. The GNU header above supplies `nds32_r45map` and
`nds32_r54map`.

## EX9 and inline-function semantics

`EX9.IT` executes an instruction selected from the instruction table at
ITB. It is not generally a software interrupt or a complete service call.
Its effects may be a load, store, arithmetic instruction, call, or other
permitted operation. The inherited labels `Service` and
`BootProfile.interrupt_table` therefore do not establish those effects.
The latter is an instruction-compression table base, not an interrupt
vector-table base.

The inherited wide EX9 encoder has the correct encoding for indices
32 through 511 but deliberately does not implement the distinct small
form. A new complete encoder should select `0xdd40 | index` for 0 through
31 and `0xea00 | index` for 32 through 511, rejecting larger values.

| Profile | Runtime instruction-table base | Corresponding file offset |
| --- | ---: | ---: |
| postmarketOS | `0x17bc0` | `0x17dc0` |
| map220v | `0x17010` | `0x17210` |

These locations come from the inherited boot profiles. Both tables are in
Agent 18's upper-ILM reservation. Agent 17 may inspect reference entries to
resolve its lower-ILM control/data flow, but must not count those table
bytes as reconstructed in its own source interval. Effects of an EX9 entry
must be checked separately, including special PC/link semantics for calls
and branches. A normal table-location disassembly alone is insufficient
to determine an EX9 instruction's effective branch target.

Other aliases needing explicit handling:

- `0x83ff` is IFRET16, not an ordinary `mov55 sp,sp`.
- IFCALL9 has an unsigned nine-bit halfword displacement.
- IFRET has a fallthrough path when the inline-function state is off;
  it must not always be treated as an unconditional conventional return.
- BEQZS8/BNEZS8 compare the implied `r15`/TA register. The inherited
  `branch_ta_zero_short()` description is correct.

Primary implementation discussions and sources:

- Ghidra EX9.IT implementation discussion:
  https://github.com/NationalSecurityAgency/ghidra/discussions/6612
- Ghidra inline-function control-flow discussion:
  https://github.com/NationalSecurityAgency/ghidra/discussions/6627
- GNU assembler BEQZS8 relaxation to `beqz r15`:
  https://gnu.googlesource.com/binutils-gdb/+/3fb6f5457e5b53fdb73a98a24b3764e821e8ccc5/gas/config/tc-nds32.c

The Andes-maintained simulator also supplies direct implementation evidence:
https://github.com/nds32/gdb/blob/master/sim/nds32/interp.c
Its `ifcall9` handler preserves IFCLP when chaining an already-active inline
call; otherwise it saves the following halfword address. The `mov55 or
ifret16` handler branches through IFCLP and clears IFCON only when IFCON
was set. Agent 17 therefore retains explicit IFC instructions and does not
replace these shared tails with ordinary call/return assumptions. The
verification report records this limitation; it does not emulate full IFC
state through each routine.

## Address and GP accounting

The reference ILM descriptor maps file offset `0x200` to SRAM address zero.
Thus Agent 17 file `[0x66a,0x10000)` corresponds to runtime
`[0x46a,0xfe00)`. Relative branch displacement calculations may use file
addresses consistently because this constant offset cancels; absolute code
addresses and ITB values must use runtime addresses.

GP-relative targets are absolute SRAM addresses, not ILM file offsets.
The inherited boot profiles use GP `0x2d9e0` for postmarketOS and `0x2d7f0`
for map220v. The inherited GP word load/store packing agrees with the GNU
decoder: signed 17-bit displacement scaled by four. No ILM file-offset
adjustment belongs in that displacement calculation.

## Independent verification requirements

Use the NDS32 GNU assembler and disassembler, with exact-width mnemonics
and assembler relaxation disabled (`-mno-all-relax`). Reassemble the
authored assembly, extract `.text`, and compare that output, the typed Rust
output, and the pinned reference interval. Independent decoding must check
instruction aliases and operands, not only instruction widths.

GNU assembler option documentation:
https://sourceware.org/binutils/docs/as/NDS32-Options.html

The existing synthetic tests exercise lengths and mismatch reporting but
mostly compare generated bytes with buffers built using the same emitter.
Such tests cannot establish reference equality or correct semantics on
their own. Required new checks should cover reserved compact branch
registers, compact register remapping, EX9 boundaries, branch alignment and
range errors, negative GP displacements, and at least one independent
assembly round-trip of a complete authored block.

### Tools actually checked during Agent 17 preparation

GNU binutils 2.43.1 built for `nds32le-elf` correctly decodes the ordinary
instructions and all six JRAL5 sites listed above. Its opcode table lacks
EX9.IT, IFCALL and IFRET entries: wide EX9 values are misleadingly printed
as BREAK16 using only the low five index bits; small EX9, IFCALL9 and
IFRET16 are printed as unknown. Do not treat this as a valid full decode.
The same toolchain cannot assemble an `ex9.it` mnemonic.

pypcode 4.0.1's `NDS32:LE:32:default` SLEIGH language independently
confirms all six JRAL5 sites and decodes the first 82-byte continuation,
including all five EX9 instructions. It does not provide complete IFC
semantics: IFCALL9 is unsupported and IFRET16 is displayed as `mov55 sp,sp`.
Consequently tool coverage must be reported per instruction family rather
than claiming a complete independent assembler/decoder check.

The first natural continuation endpoint is file `0x6bc` (runtime `0x4bc`),
after POP25 at file `0x6ba`, completing the reset helper begun at `0x5de`.
The new span `[0x66a,0x6bc)` contains 25 instructions: sixteen 32-bit and
nine 16-bit instructions, including five EX9 forms. Both firmware revisions
have the same widths and endpoint. Its three distinct EX9 table operations
are INT_MASK2 write, INT_MASK3 write, and `ori r0,r0,1`; these table words
are independently decoded as ordinary 32-bit instructions by GNU binutils.
No additional instruction-table coverage is claimed from that inspection.

This audit establishes encoding defects and interpretation limitations.
It does not establish a complete hardware model, full source-level
decompilation, device execution, or flashable firmware.
